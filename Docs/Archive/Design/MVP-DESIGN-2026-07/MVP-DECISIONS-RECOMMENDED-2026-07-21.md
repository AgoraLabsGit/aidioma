===== provider-model =====
**RECOMMENDATION:** Route all AI calls through Vercel AI Gateway (via the Vercel AI SDK, zero markup, BYOK-capable) with **`openai/gpt-5-mini` as the default evaluation model** and **Anthropic `claude-haiku-4-5` as the baked-in runner-up** for the 20-sentence bake-off; expect roughly **$3–19/month** in AI spend at 100 active users.

**Why:**

**(a) Gateway vs direct SDK — Gateway.** As of mid-2026 Vercel AI Gateway passes through provider list prices with **zero markup** (including BYOK), gives every team **$5/month in free credits**, and its only fees are opt-in add-ons (team-wide ZDR/allowlist at $0.10/1k requests) you won't enable ([Vercel pricing docs](https://vercel.com/docs/ai-gateway/pricing), [fee comparison](https://llmgateway.io/blog/ai-gateway-fees-compared)). It supports hundreds of models across OpenAI, Anthropic, Google, Moonshot, etc. ([Vercel AI Gateway](https://vercel.com/ai-gateway)), so the W2 bake-off and any future model swap is a one-line model-string change behind your single EvaluationService — no second SDK dependency. Wrap it in your own `EvaluationService` interface anyway (already the plan), so falling back to a direct SDK is a ~1-file change if the Gateway ever becomes a problem.

**(b) Default model — `gpt-5-mini`.** Current pricing is **$0.125/M input, $1.00/M output** ([pricepertoken](https://pricepertoken.com/pricing-page/model/openai-gpt-5-mini), [TLDL OpenAI pricing](https://www.tldl.io/resources/openai-api-pricing)) — roughly 8× cheaper than Haiku 4.5 on input — with first-class strict JSON-schema output, which is exactly what a fixed-enum `errorTags` + score + 2-3-sentence feedback payload needs. Note OpenAI's newer GPT-5.6 family (Sol/Terra/Luna, launched July 9 2026) starts at $1.00/M input for Luna ([aipricing.guru](https://www.aipricing.guru/openai-pricing/)) — the older mini tier remains the value pick for this call shape. GPT-5 nano ($0.03/M input, [finout](https://www.finout.io/blog/openai-pricing-in-2026)) is tempting but too weak a margin of safety for pedagogical error-tagging; the entire cost delta from nano→mini is under $2/month at your volume.

**(c) Runner-up for the bake-off — `claude-haiku-4-5`** ($1.00/M input, $5.00/M output, 200K context — current Anthropic small tier; your hardcoded `claude-3-haiku-20240307` is past its Apr 2026 retirement and must go regardless). Rationale: Claude models are consistently strong at nuanced, encouraging feedback prose — the one part of this call a learner actually reads — and your surviving claude-mvp code already speaks Anthropic prompt shape, so it's a cheap A/B. Skip Kimi K2.x (now $0.60–0.95/M input for K2.5/K2.6 ([tokenmix](https://tokenmix.ai/blog/kimi-k2-api-pricing), [OpenRouter K2.5](https://openrouter.ai/moonshotai/kimi-k2.5)) — a big agentic model at near-Haiku prices with worse latency for a 1-second grading call). If you want a third lane, add **Gemini Flash-Lite** ($0.10–0.25/M in, $0.40–1.50/M out ([cloudzero Gemini pricing](https://www.cloudzero.com/blog/gemini-pricing/), [TLDL Gemini](https://www.tldl.io/resources/google-gemini-api-pricing))) as the floor-price contender; DeepSeek V3.2 ($0.28/$0.56, [OpenRouter](https://openrouter.ai/deepseek/deepseek-v3.2)) saves nothing meaningful over mini here.

**(d) Cost at 100 users × 20 items/day, 80% gate hit:** 20% of 2,000 daily items reach AI = 400 calls/day ≈ **12,000 calls/month**. Assumptions: ~800 input tokens/call (system prompt + tag enum + reference + alternates + user answer) and ~150 output tokens (JSON: score, 2-3 sentences, tags) → 9.6M input + 1.8M output tokens/month. That's **~$3.00/mo on GPT-5 mini**, ~$5/mo on Gemini Flash-Lite or Kimi K2.5, **~$18.60/mo on Haiku 4.5** — i.e., even the most expensive candidate is pocket change, and prompt caching on the shared system prompt cuts input cost further. Conclusion: pick on evaluation *quality* (error-tag accuracy + feedback usefulness in the bake-off), not price — every candidate is within noise of free at MVP volume.

**Caveat/revisit trigger:** Two triggers. (1) **Week 2, before committing:** my fetch of the Gateway model catalog surfaced only the newer flagship tiers (Sonnet 5, GPT-5.6, Kimi K2.7) — spend 30 minutes confirming `gpt-5-mini` and `claude-haiku-4-5` are actually routable through the Gateway (catalog page may have been a featured subset); if either is missing, use BYOK or drop to the direct OpenAI SDK behind the same EvaluationService interface — the decision architecture doesn't change. (2) **Wave 3 (conversations):** the calculus flips — no comparison gate, multi-turn context, persona quality matters, and volume per session is ~10× — re-run the bake-off then with conversation transcripts, likely landing on a stronger model for dialogue turns while keeping mini for evaluations. Also reopen if the bake-off shows error-tag accuracy below ~85% agreement with your human labels on mini — step up to Haiku 4.5 or Gemini Flash and eat the still-trivial cost.

===== content-ops =====
**Q2 — Start-level story with A1-only content**

**RECOMMENDATION:** Do not author A2 lessons pre-launch; self-identified A2/B1 users start with all 12 A1 lessons **unlocked** (mastery-gating waived for them), land on Lesson 1 with an honest banner — "Our content currently covers A1. Use it as a fast review; A2 arrives in [month]" — and A2 authoring becomes the week-7+ parallel track alongside Reading.

**Why:** Starting an A2 user "partway in" is dishonest and pedagogically broken — the A1 spine is a vocab/grammar dependency chain, and Lesson 8 assumes items from Lessons 1–7, so a mid-spine start produces a first session full of untaught vocab, which violates the consensus's own "no quiz on material never presented" principle. Authoring A2 pre-launch is the worst option: it delays the 6-week ship for users who are not the launch ICP, and the content pipeline (contract + CI + `content:draft`) is deliberately designed to make post-launch authoring cheap and parallel — spending that capacity before you know whether *anyone* at A2 shows up is the exact horizontal over-build the review diagnosed. Unlocking the full A1 set for A2+ self-identifiers is the honest middle: they aren't forced to grind mastery gates on trivial content, they can skim the Library and cherry-pick weak spots (blend/review recipes already support this), and many self-labeled "A2" learners have real A1 gaps (ser/estar, gender agreement) that a fast pass genuinely serves. It also costs roughly one `if` statement — `user.level > 'A1' ⇒ status: active` on seed — against the already-decided `user_lesson_progress` model. Finally, it keeps marketing honest: position the launch as "beginner Spanish, A2 coming," and the banner converts a weakness into a roadmap promise.

**Caveat/revisit trigger:** Reopen if launch-week onboarding data shows >~30% of sign-ups self-selecting A2+ *and* their day-2 retention is materially worse than A1 users' — that's the signal to pull A2 authoring ahead of Reading in the fast-follow order. Also revisit the "all unlocked" waiver if A2+ users skip straight to Lesson 12, fail, and churn; the fix then is a lightweight "quick check" per lesson, not a placement test.

**Q3 — Content review bar**

**RECOMMENDATION:** Ship a four-layer gate — CI validator → adversarial second-LLM pass → founder checklist review → **one paid native-speaker full review of all 12 launch lessons (~$200–400 one-time, e.g. an italki/Preply tutor at $20–30/hr for 8–12 hours)** — plus an in-app "report this sentence" flag button, with native review dropping to a 25% sample for post-launch lessons.

**Why:** The founder-as-bottleneck fear is overstated at MVP scale: 12 lessons ≈ ~150 vocab + ~200 sentences + 12 explanations, and A1 content sits comfortably *below* intermediate competence, so the founder can catch most errors himself — what he can't reliably catch is naturalness and regional register, which is exactly what the one-time native pass covers, and at ~420 items a working tutor reviews the whole launch corpus in one or two paid sessions (~2 min/sentence-cluster ⇒ 8–12 hrs ⇒ $200–400 at $20–30/hr on italki/Upwork; brief them to redline, not rewrite). The adversarial LLM pass (a *different* frontier model prompted as a pedantic native editor, structured output against the checklist below) costs pennies per lesson and catches 80% of drafting-model blind spots before any human time is spent. The flag button is non-optional: the dominant failure mode won't be wrong Spanish, it will be **missing accepted alternates** — a user's valid answer scored wrong — and no amount of pre-launch review finds those; only real submissions do, so wire flags to a weekly triage → add alternate → `contentVersion` bump loop. Acceptable error bar at MVP: **<1% linguistic errors in displayed model content** (post-native-review this is achievable; an error in *taught* material destroys trust disproportionately), but tolerate ~5–10% of early submissions hitting alternate-coverage gaps and ~5% tag misclassification (low user-visible harm; it only slightly miscalibrates the blender).

**The checklist (used by both the LLM pass and the founder, per lesson):**
1. Every `es` string grammatically correct — accents, gender agreement, conjugation match the stated tense.
2. Naturalness — no anglicisms or literal calques; "would a native actually say this?"
3. Register consistency — pick **neutral Latin American Spanish, tú throughout** (decide once, write it in the authoring prompt); no vosotros, no region-locked slang.
4. `en` translations accurate *and* natural English.
5. Alternates: 3–6 per direction present; include pronoun-drop variants, contractions, common synonyms; read each and ask "would I accept this?" — this line item is the cost gate's fuel.
6. Vocab leakage — sentences use only this lesson's + prior lessons' vocab (CI checks `vocabRefs`; humans check the free text).
7. Hints escalate properly — level 1 nudges, level 3 near-reveals, none is the literal answer.
8. `grammarTags` match what the sentence actually exercises.
9. Explanation ≤150 words, rule stated correctly, inline examples actually demonstrate the rule.
10. Difficulty 1–5 plausible relative to the lesson's other sentences.

**Caveat/revisit trigger:** Reopen when output passes ~4 lessons/week or a second language ships — that's when a standing paid reviewer relationship (retainer, not spot-checks) beats ad-hoc sampling. Also reopen immediately if flag volume exceeds ~5% of sessions or any *taught-content* error survives to a user report twice — that means the sample rate for new lessons must go back to 100% native review.


===== product-metrics =====
**Q4 — Success metric**

**RECOMMENDATION:** Adopt the panel's metric with two modifications — widen "day 7" to a day 5–9 window and pin "completed session" to a concrete, queryable definition — making the single MVP metric **W1 Completed-Session Return: % of new users who complete ≥1 full session during days 5–9 after their first evaluation**, measured directly from the `evaluations` table plus one added `sessionId` column.

**Why:** The day-7 instinct is right — it separates "tried it" from "adopted it" — but a literal day-7 point measurement is statistically useless at MVP user counts (a user returning day 6 or day 8 is the same signal), so a 5-day window around day 7 is the honest version. "Completed session" must be defined mechanically or the metric is unfalsifiable: since the SessionEngine already generates a recipe of fixed size 10, have the client stamp every `EvaluationRequest` with a UUID `sessionId` (one nullable column on `evaluations`, added in W3 when the persistence loop is built — this is not analytics infra, it's provenance on data you're already writing). A completed session = a `sessionId` with ≥8 evaluations. The whole metric is then one saved SQL query run by hand weekly: cohort users by `MIN(createdAt)` in `evaluations`, count those with a qualifying session whose first evaluation falls 5–9 days later. Add one guardrail metric, also free from existing tables: **median time from `users.createdAt` to first evaluation < 90 seconds** — this protects the panel's first-session target and catches onboarding regressions that retention won't reveal for a week.

**Decision rule:** (1) Every post-MVP feature proposal (conversations, real SRS, manual blends, reading direction #2) must state, in one sentence, why it will raise W1 return — if you can't write that sentence, the feature waits. (2) Establish baseline over the first ~50 signups; if baseline is below ~20%, freeze all new features and fix the core loop (content quality, session summary, blend) instead. (3) After shipping any feature, compare the next 4 weeks of signup cohorts against baseline; no movement after 4 weeks means stop investing in that feature.

**Caveat/revisit trigger:** Reopen when either (a) weekly signups exceed ~200, at which point graduate to a real event pipeline and proper cohort curves (D1/D7/D28), or (b) you start paid acquisition, where cost-per-retained-user replaces raw retention as the decision metric. Also revisit the ≥8-of-10 threshold if session recipes stop being fixed-size.

**Q5 — Streak / notification posture**

**RECOMMENDATION:** Ship a **calendar-day streak (user's local timezone) that counts only completed sessions, with one automatic rest day per rolling 7 days, derived at read time from the `evaluations` table — and zero reminder notifications of any kind at MVP.**

**Why:** *No notifications:* Clerk sends auth emails, not marketing/reminder emails — "reminders via Clerk" would actually mean adding an email provider plus a cron job plus unsubscribe handling, which is real build cost for a channel that mostly nags users who were leaving anyway; at MVP scale the product has to earn returns on its own, and that keeps your W1-return metric uncontaminated as a baseline. *Calendar-day over 24h-rolling:* rolling windows create invisible deadlines and anxiety (practice at 9pm, lose the streak at 9:01pm tomorrow) — that's the dark-pattern texture the panel rejected; store timezone on the `users` row at signup and bucket by local date. *Completed sessions only:* if the streak counts any stray evaluation, it rewards streak-farming with one flashcard flip, decouples from your success metric, and lies about learning — protecting the same unit Q4 measures makes the streak, the session summary, and the metric one coherent loop. *One automatic rest day per rolling 7:* this is a grace rule, not an inventory — no freezes to earn, buy, or manage; a single missed day within any 7-day span doesn't break the streak, and the UI says so plainly ("Rest day used — streak safe"). *Derived, not stored:* the review already decided streak is computed on read from evaluations; the whole feature is one SQL/date-walking function over completed-session days plus a number on the Home streak strip — near-zero build cost and it can never drift out of sync with reality.

**Caveat/revisit trigger:** Reopen notifications only after the Q4 baseline exists and shows a concentrated day-2/3 dropoff — then add exactly one opt-in (unchecked by default) daily reminder email via a free-tier provider (e.g., Resend) and judge it by whether it moves W1 return, not by open rates. Reopen streak mechanics if user feedback shows the rest-day rule confuses more than it comforts, or if completed-session counting proves too strict for mobile users doing short bursts — in which case loosen to "any completed session OR ≥15 evaluations in a day," never to "any activity."


===== pedagogy-eng =====
**D1 — Vocab load per lesson**

**RECOMMENDATION:** Adopt an authoring guideline of 10 new vocab items per lesson (acceptable range 8–12), keeping 15 as a hard schema ceiling reserved for phrase-heavy lessons.

**Why:** The pedagogy evidence is one-directional — retention per item degrades past ~10 new items per session, and there is no counter-evidence that fatter lessons improve outcomes; the pragmatist's argument is really about total content volume, which is solved by authoring more lessons, not denser ones. With LLM-assisted drafting against a frozen contract, the marginal cost of a 13th lesson is low, so throughput is not actually gated by items-per-lesson. Leaner lessons also shrink the QA surface per lesson (fewer sentences needed to exercise every vocab item, fewer alternates to review), which matters when the founder is the sole reviewer. Finally, 10-item lessons make the mastery computation (≥70% of vocab reviewed twice) reachable in one or two short sessions, which protects the "first evaluated answer in under 90 seconds" and daily-completion loop. The blend algorithm assumes small, well-tagged lessons to interleave — bloated lessons blunt it.

**Caveat/revisit trigger:** Revisit if authoring throughput genuinely becomes the launch bottleneck (fewer than 12 lessons ready by W5), or if post-launch data shows users completing lessons far faster than the content pipeline replenishes them; in that case raise the guideline to 12–15 before adding lessons beyond A1.

**D2 — Mastery spacing**

**RECOMMENDATION:** Require the different-day rule — a lesson reaches "Mastered" only after ≥2 successful retrievals of its vocab on at least two distinct calendar days — but split the UI into two explicit states: "Completed" (same-day, full celebration, next lesson unlocks) and "Mastered" (confirmed next day), so spacing never blocks progression.

**Why:** The pedagogy objection is correct on the science (same-day mastery is fluency illusion), but the UX objection is correct that invisible friction is unacceptable — so decouple the two things the single "mastered" flag was conflating: *unlock* and *mastery*. Concretely: acing a lesson marks it **Completed** and unlocks the next lesson immediately, so a motivated user is never told "you can't proceed for a reason we can't explain." The lesson flips to **Mastered** only when the blender serves its items again on a later day and the user hits the ≥70% bar a second time — which the 60/40 blend already does automatically, so no new mechanism is needed. The UI copy is one sentence on the session summary and lesson card: "Completed ✓ — comes back tomorrow to confirm mastery," which is both honest and a built-in reason to return (it directly serves the day-7-return metric). Implementation is the promised one-line change: `masteredAt` requires a qualifying evaluation whose date differs from the completion date; `user_lesson_progress.status` gains one value (`completed`).

**Caveat/revisit trigger:** Revisit if session summaries show users confused by the Completed/Mastered distinction (support questions, rage-taps on the mastery bar) or if analytics show the "confirm tomorrow" prompt doesn't move day-2 return — then simplify to same-day mastery rather than adding explanation UI.

**D3 — Direction policy at launch**

**RECOMMENDATION:** Launch typed translation EN→ES only; flashcards both directions; add ES→EN typed as a toggle in the W7–8 fast-follow alongside Reading.

**Why:** EN→ES production is where typed translation earns its keep pedagogically — recognition-direction practice (ES→EN) is largely covered at launch by ES→EN flashcards, so shipping both typed directions buys little incremental learning value for double the cost-gate surface. The comparison gate "lives or dies on alternate coverage," and alternates are the single most review-intensive authoring artifact: EN→ES needs `acceptedEs[]` (constrained target language, fewer plausible variants), while ES→EN needs `acceptedEn[]` where English paraphrase space is much wider and misses fall through to paid AI calls. Halving that surface across 12 lessons × 12–20 sentences is the difference between the founder QA-ing 12 lessons well or 12 lessons badly. The schema keeps both direction fields and `direction` is first-class on every evaluation, so nothing is lost structurally — ES→EN typed is a UI toggle plus an alternate-authoring pass, and it lands naturally with Reading (also ES→EN comprehension) in W7–8. This also matches the pragmatist's clean per-modality direction map: typed = production, reading = comprehension, flashcards = both.

**Caveat/revisit trigger:** Reopen at W7–8: if AI-call rate on the EN→ES gate is low (alternate coverage proved manageable) and the LLM drafting step is reliably producing good English alternates, enable ES→EN typed with Reading; also reopen immediately if early users explicitly ask for comprehension-direction typed practice.

**D4 — evaluationCache table**

**RECOMMENDATION:** Drop the table in the W1 migration; do not build the cross-user persistent cache at MVP — but keep the door open by logging `evalSource` and a `normalizedInputHash` column on `evaluations` from day one.

**Why:** The architecture idea is sound *at scale*, but the math doesn't work at MVP scale: a cross-user cache only hits when two different users produce the byte-identical normalized wrong answer to the same item in the same direction — and every *right or near-right* answer is already caught free by the comparison gate, so the cache only ever intercepts the residual AI-path traffic of a user base measured in dozens. Expected savings are single-digit dollars per month against real costs: another table to migrate, invalidation on `contentVersion` bumps, staleness when the eval prompt or model changes, and one more code path to test in the very service the plan is consolidating from 4,900 lines to ~500. The orphaned table is also a live example of the project's core disease (designed infrastructure the app ignores) — deleting it is on-message for this MVP. Crucially, dropping it destroys no information: since every evaluation row records `evalSource`, `itemRef`, `direction`, and (add this now, it's one column) the normalized input hash, you can compute the exact would-have-been hit rate from production data before writing a line of cache code.

**Caveat/revisit trigger:** Revisit when monthly AI spend exceeds ~$50 or a query over `evaluations` shows >15% of AI-path calls share an (itemRef, direction, normalizedInputHash) with a prior call — at that point rebuild it as a cache keyed exactly as architecture proposed, invalidated by `contentVersion`.
