# Which fields belong in Feature–Release molds?

## Question

Thin living stubs (D-013) tag Work, but Rules are often vague. Choose **keep / trim / add**
for Feature, Area, Product, Phase, Research, Decision, Release so molds guide real
development — actionable fields only; no Docs.2 essay return.

## Evidence

| Source | Keep |
|---|---|
| Living Spec templates | Already have Purpose / Behavior Rules / Boundaries / Failure mode |
| Living stubs (Practice, Progress, …) | Tags work; Rules like “primary surface” are not checkable |
| `Docs.2/Specs/*` | Outcome, claim tables, open questions, long acceptance — evidence only |
| Peer shapes | ADR (Context/Decision/Consequences); RFC design docs; Gherkin AC; YAML-only |

## Options

### Specs (Feature / Area) — primary gap

| Option | Strengths | Costs | Notes |
|---|---|---|---|
| A. Status quo templates | Stable Knowledge/CI | Vague stubs persist | Does not meet phase outcome |
| B. Docs.2 dossier sections | Rich AC / claims | Cap break; unconsumed essays | Reject |
| C. Frontmatter-only / YAML specs | Machine-first | Unreadable in Knowledge | Reject |
| D. ADR block on every Feature | Why local to file | Dupes `DECISIONS.md` | Reject |
| E. **Keep sections; define Rule grammar + stub bar** | Fixes real gap; no new essay homes | Needs sample refine | **Choose** |
| F. Schema-count Rules in CI | Enforceable | Prose lint cost now | Defer — Revisit if |

**Rule grammar (E):** present tense; observable (UI/API/file/CI); fail-visible. Bad: “is the
primary surface.” Good: “Practice UI is the only learner route that starts a scored attempt.”

**Stub bar (E):** Purpose ≤3 sentences; ≥1 Rule meeting grammar; Boundaries non-empty;
Feature Dependencies names areas; Area Failure mode non-empty. MOCK fixtures exempt.

### Product / Release

| Option | Strengths | Costs |
|---|---|---|
| A. Leave format only inline in `PRODUCT.md` / `RELEASES.md` | No new files | No Templates/* mold for two families |
| B. **Migrate format SSOT into `Templates/product.md` + `release-entry.md`; living files keep content** | One mold home; no duplicate authority | Small move | **Choose** |
| C. Add new Product/Release sections now | — | PHASE-002 / first `/ship` own depth | Reject |

### Phase / Research / Decision

| Option | Verdict |
|---|---|
| Keep current fields | **none** (no field-set change) |
| Trim Inputs / Adv / Affects | Reject — still development-critical |
| Add peer ADR/RFC sections | Reject — homes already correct |

## Verdict

1. **Specs — E:** Keep V3 sections. Amend Spec templates with Rule grammar + stub bar (guidance,
   not new sections). Refine ≥1 Feature + ≥1 Area living stub to the bar (non-MOCK).
2. **Product / Release — B:** Templates become format SSOT; no new product/release fields.
3. **Phase / Research / Decision:** keep-as-is (`none`).
4. **Reject** B/C/D for Specs; **defer** F.

## Adv

`ADV: PASS` — Required Adv (sub-agent). Prior FAIL fixed: Specs = keep + Rule grammar/stub bar
(not fake field adds); peers dispositioned; Product/Release = format SSOT migrate only.

## Revisit if

- First real Feature `/close` fails path→spec for lack of a named field (then add that field only).
- Vague Rules recur after stub bar → enable option F (CI prose check).
- First real `/ship` needs Release evidence beyond Date/Phase/summary.
- PHASE-002 changes Product sections (amend Product template only).
