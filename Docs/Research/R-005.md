# Further mold changes after D-028–D-030?

## Question

D-028–D-030 locked Spec Rule grammar, Product/Release template SSOT, and unchanged
Phase/Research/Decision molds. Do **generic software** peer practices require more field-set
changes now? (Must not overfit to any one product domain.)

## Peer farm (online, 2026-08-08)

| Family | Peer pattern | Keep for us | Reject / defer |
|---|---|---|---|
| **Feature** | Testable AC; rule-checklist **or** Given/When/Then; outcomes not implementation ([spec-coding](https://spec-coding.dev/blog/how-to-write-technical-spec-template-guide), BDD guides) | Checkable Rules (D-028) = rule-oriented AC | Mandatory GWT in every Spec (ceremony for thin living specs) |
| **Area** | Platform/service ownership: boundaries, failure modes, who observes downtime ([SRE/ownership](https://sreschool.com/blog/service-ownership/), Team Topologies) | Boundaries + Failure mode already in Area mold | Full ownership packets / on-call registries in Spec body |
| **Product** | Lean PRD: who, capabilities, **non-goals** high value; fat 10–12 section PRDs optional ([PRD guides 2026](https://docsio.co/blog/prd-template)) | Who / What / Never / Principles | Shipping goals-metrics-stories-NFR into permanent Product file |
| **Phase** | Design doc / RFC: problem, non-goals, success/proof, alternatives ([RFC/design-doc](https://docsio.co/blog/design-doc-template)) | Outcome + non_goals + proof + plan | Merging alternatives into Phase (that is Research) |
| **Research** | RFC “alternatives considered” (≥2 options, verdict) | Options table + verdict + revisit | Essay design-doc body as Research home |
| **Decision** | Nygard / lean [MADR](https://adr.github.io/madr/): context, choice, why, supersede; Consequences optional | Chose / Why / Revisit / Supersedes | Full MADR drivers + pros/cons tables on every Decision |
| **Release** | [Keep a Changelog](https://keepachangelog.com/en/2.0.0/): dated entries; Added/Changed/… categories; ship notes ≠ full changelog | Date + id + summary ship log | Six categories + Unreleased **now** (no real ships yet) |

Cross-cutting: C4/DDD “area vs feature” maps to Area substrate vs Feature capability — already our split.
Homes stay separate (Product ≠ Spec ≠ Decision ≠ Research ≠ Phase ≠ Release).

## Options

| Option | Strengths | Costs |
|---|---|---|
| A. **Defer further field-set changes** (MCOO timing) | Ships lean core now; peer extras wait for consumers | Does not claim peers prefer “never add” |
| B. Require Given/When/Then for every Spec Rule | Stronger testability | Ceremony for thin living specs; D-028 already pass/fail |
| C. Expand Release mold to Keep a Changelog categories now | Peer-normal ship notes | Unconsumed — zero production ships |
| D. Add MADR Consequences (+ drivers) to Decision mold | Peer-normal ADR richness | Dupes Why/Revisit until Decisions lose “what hurt” |
| E. Add success metrics section to Product mold | Peer-normal PRD metrics | Unconsumed until Product is filled |

## Verdict

**A — defer, not “peers said no.”** Peers treat GWT, KaC categories, MADR Consequences, and PRD
metrics as **normal extras**. We defer them because nothing consumes them yet (MCOO), not because
peers reject them. Living molds already cover the **lean core** peers also require: testable Rules,
Area failure modes, lean PRD + non-goals, RFC alternatives → Research, choice → Decision, dated
ship log → Release. Homes stay separate. Not domain-specific.

1. Specs: keep rule-oriented AC (D-028); do not mandate GWT now.
2. Areas: keep Boundaries + Failure mode.
3. Product: keep Who / What / Never / Principles; metrics later.
4. Phase / Research / Decision: keep current split (alternatives in Research, choice in Decision).
5. Release: ship log now; KaC categories at first real production ship.

Guidance polish under D-028 (no new fields / no new decision): Spec templates note Rules are
rule-oriented checklists (peer alternative to GWT).

## Adv

`ADV: PASS` — Required Adv after WARN fix (defer = MCOO timing; peers name extras as normal).
Design-review panel A-037: **PASS**, agree verdict A, recommended now: none.

## Revisit if

- A Feature close needs scenario AC (then allow GWT as optional Rule form, not required).
- First production `/ship` needs categorized user-facing notes → adopt KaC categories.
- Decisions keep losing “what hurt” → add optional Consequences line (supersede D-030 for that field only).
- Product fill stalls without metrics → add one Goals line to Product template only.
